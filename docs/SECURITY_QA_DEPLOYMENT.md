# Security, verification and operations
## Threat model and controls
Threats: crawler SSRF/injection, malicious uploaded documents/media, hallucinated marketing, leaked OAuth tokens, unauthorized publish/ad spend, cross-tenant IDOR, webhook replay, duplicate jobs, race conditions, stale product pricing, malicious redirect, provider outage, analytics privacy leakage. Controls: schema validation and escaping, allowlisted egress, isolated browser/FFmpeg with CPU/memory/time/output limits, malware/file validation, least privilege RBAC and MFA for privileged users, CSRF protection and secure cookies, encryption at rest/in transit, secret vault/key rotation, scoped row queries and foreign keys, signed webhooks, audit redaction, idempotent outbox/reconciliation, approval-bound hashes, atomic reservations and fail-closed policy. No AI access to credentials, raw personal data or unrestricted tools; never send confidential docs to external model without approval. Separate read permissions from publish and financial authority. Production keys unavailable in test. Audit log retention and privacy/data deletion policy approved before release. Verify dependencies/licenses and SBOM; no unapproved assets or customer data. Legal/privacy review required, do not claim compliance.
## Quality strategy
Use pytest with temporary PostgreSQL/Redis services, mocked adapters and deterministic clock; frontend Vitest/React Testing Library and Playwright, accessible and visual verification. Test writer reads specs and modifies tests only; runner executes independently, records real output. Integration tests cover migrations, transactions, queue crash recovery, HTTP/provider contracts and webhook signatures. Provider live tests only on approved assets, authorized limited budgets and explicit action permission. No real publishing, notifications, paid API charges or ads from CI. Record IDs, setup, data, exact steps, expected/actual, status, evidence, defect, coverage and residual risk.

## Combination testing
Enumerate platform × format × automation mode × approval state × account state × scheduling state; constrain by confirmed provider capabilities, explicitly test invalid combinations, exhaustive where small and pairwise/3-way for larger sets. Advertising: objective × existing/new creative × placement × daily/lifetime × permission × budget state × remote review state. Prioritize all spend/approval/race/pause combinations. Include retry after timeout, kill switch during claim and activation, currency mismatch, stale reports, dashboard state. Produce generated matrix with theoretical/valid counts, executed coverage and gaps; no fabricated results. Proposed target: every mandatory acceptance criterion mapped to at least one executed check before pilot; actual performance/coverage thresholds approved after baseline.
## Deployment and DevOps
Development with mock mode and `.env.example`; test and staging separate from prod. CI: lint, typecheck, unit/integration/E2E, migration validation, dependency and secret scans, image builds/SBOM; require reviewed PR, approved release, backup and rollback plan. Docker Compose services: frontend, api, PostgreSQL, Redis, scheduler, workers, render worker, reverse proxy; object storage/internal approved service. Run non-root, limits, read-only FS where appropriate, separate volumes, internal DB/Redis networking, TLS, restricted firewall and secret custody. No automatic production deploy on every commit. Verify versions, paths and shell instructions for Windows PowerShell/Linux; explicit commands generated after repository/host discovery. Initial local `docker compose config`, `docker compose up -d`, `docker compose ps`, `docker compose logs` only when actual Compose exists and user approves setup. CI scripts and deployment instructions must be tested, not claimed executed here.
## Config contract
Document env variables for DATABASE_URL, REDIS_URL, APP_BASE_URL, SESSION_SECRET, token encryption key reference, storage endpoint/bucket, provider API keys/model alias, Meta/LinkedIn/X app credentials, OAuth redirect base, approved source hosts, timezone and budgets. Feature flags `LIVE_PUBLISH_ENABLED=false`, `LIVE_ADS_ENABLED=false`, `PAID_GENERATION_ENABLED=false`, `AUTOPILOT_ENABLED=false`, `MOCK_PROVIDERS=true`; flags never bypass authorization. Fail startup if live mode missing required config; validate currency and cap settings. Never seed real keys. Use per-environment secrets, OAuth callback origins, rotating encryption keys with tested recovery.
## Observability and incident runbook
Metrics: ingestion freshness, scheduler lag, queue depth, unknown publications, token expiry, provider latency/errors/429, generation rejection and spend, ad reconciliation age, pause confirmation, database saturation, backup success and restore recency. Structured redacted logs and correlation IDs. Alert on duplicate suspicion, stale spend, provider failures and unusual costs. Incident: disable local dispatch, request remote pause, verify provider state via authorized console if API unavailable, isolate affected credentials, preserve audit evidence, reconcile outstanding jobs and spend, review root cause, explicitly authorize recovery. Published posts cannot be unposted by local rollback. Document on-call ownership.
## Recovery and handover
Back up DB and asset objects/manifests, encrypted token data and necessary key recovery material separately, test restore in isolated environment with outbound side effects disabled. Reconcile remote state before reenabling workers following restore. Define RPO/RTO, retention, encryption, offsite copies and restore evidence after owner approval. Release checklist: approved scope, migrations, tested backup/rollback, TLS/health, CI evidence, config validation, security, live credentials, permission review, smoke and monitoring, signoff. Deliver user guide, admin guide, API docs, ADRs, ERD, test report and operational runbooks. No production-ready claim until gates pass.
